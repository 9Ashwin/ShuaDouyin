# 平台事实与已知限制

这些都是真实页面上验证过的，不是推测。读它们能省掉一次踩坑。

## 读不到的东西

**直播画面是 canvas。** `live.douyin.com` 的画面里没有任何文字层，`innerText` 拿不到游戏名、英雄、比分、经济。`live info` 的 `video_readable` 恒为 `false`。

从截图推断具体英雄是被验证过会出错的做法：一次走查里凭技能图标猜了一个英雄，观众当场质疑，事后确认猜错。**只能说屏幕上写着的字**（如「准备好你的赛前配置！」），不说需要连续观察才得出的结论（「这波团赢了」「他要玩中路」）。要看懂实况必须连续高频截图并对比，单帧不作为判断依据。

**作品作者在部分页面为空。** `video info` 的 `author` 来自详情卡里第一个有文字的 profile 链接；某些布局下它为空，但 `author_id` 仍可取到。用 ID，不要用名字。

## 会读错的东西

**点赞/收藏状态有两个反向拼写。** 页面用 `data-e2e-state`，值是 `video-player-no-digged`（未赞）和 `video-player-is-digged`（已赞）。两者都以 `-digged` 结尾，按后缀匹配会全部读成「已赞」，导致取消点赞永远确认不了。必须整体匹配 `is-` / `no-` 前缀。收藏同理，词干是 `collect` 不是 `collected`。

**`video.info` 的 `author` 不是身份。** 显示名会重名、会改。稳定标识是 `author_id`。

**评论行的作者链接可能指向 `/user/self`。** 那是路由别名，不是账号 ID。真实的 ID 在页面登录态里（`userInfoStore.curLoginUserInfo`），CLI 已从此处读取。

**自己的评论在推荐流里不会带「我的」标记。** `mine` 由 `authenticatedUser()` 判定的 ID 与行作者 ID 比对得出，不要靠界面标记。

## 会失败的东西

**私信面板挡住所有读作品的操作。** 面板是 336×678 的侧边浮层，作品在它后面完好。CLI 的读类命令会先自动关面板；关不掉时（草稿未发）会明确报错。**不要用 `chat close` 硬关**——草稿会丢。

**连续滑动会触发人机验证。** 实测连刷 20 次里 9 次返回 `verification_required`。这是平台侧的反自动化，不是命令缺陷。需要真人在 headed Chrome 完成滑块验证。**不要尝试绕过。**

**滑片过渡期读不到作品。** 点赞后立刻发下一条命令，页面正处在两张滑片之间，会读到「当前是直播」。CLI 的读命令会等过渡落地，但直播滑片不等待——那是真实站点，要由调用方决定跨过去。

**`feed open` 可能落在直播上。** 推荐流把直播当普通站点。CLI 会自动前进一步到作品，返回 `slide.skipped_live` 说明曾经路过。

## 需要核对的写入

**礼物会花钱，且类名每次构建都变。** 只能用可见文本定位（形如「15钻加油鸭15钻赠送」）。一次走查用宽泛的类名选择器点了一下，实际送出「人气票 ×2 + 加油鸭 ×1」，比预期多也更贵。

用 `live gift --name <名字> --price <单价>`：名字和价格必须同时匹配面板，点击后读聊天区确认实际送出了什么，不一致时 `unexpected` 会列出多送的东西。

**`comment.reply` 记录的是被回复评论的作者，不是作品作者。** 两个不同的人。作品作者另存为 `work_author_id`。

**评论发出的确认依赖页面标记。** 推荐流的评论区不暴露自己的真实 ID 时，`comment post` 会返回 `delivery_uncertain`——这是诚实的，不是失败。**核对收据和页面，不要换 request ID 重发。**

## 会话与群聊

- 群聊会话的稳定 ID 只在 React fiber 的会话对象原型上，只读自身属性取不到；群消息行的 ID 同样只在 fiber 的 `message.serverId` 上，DOM 里没有。
- 群消息的 `createdAt` 是页面自己给的创建时间，它是「这条是我刚发的」唯一可靠的顺序证据。DOM 先后顺序不算。
- 群里 @ 某人：先打 `@` 等选择器，点中后编辑器里是带 `data-uuid` 的节点，不是纯文本。发送后行文本为 `@名字 正文`。
- 右键消息点「回复」进入引用回复，引用状态在输入框上方的引用块里，不在编辑器文本里。
- `chat.close` 会关掉遮挡作品的私信面板。**有未发出的草稿时它会拒绝**，草稿不会丢。

## 详情页和推荐流不是同一套

直接 `dy video open <id>` 打开的是详情页，它的评论区结构和推荐流里的不一样。推荐流里能用的定位在详情页可能失效，反之亦然。`comment list` 已经处理了两种，但看原始报错时要记得这一点。

## 评论区不是评论视频的

真实评论区里大量是自我表达。一条讲小说的视频下面，十几条评论全在聊小说人物，没有一条说视频。`comment list` 给每条返回 `stance`：

- `about_work` — 在说作品（唱功、剪辑、旋律）
- `about_self` — 在说自己（「每次听到这首歌鸡皮疙瘩都起来了」）
- `asking` — 在问作者或观众
- `spam` — 引流
- `unknown` — 判不了，约六成

**`unknown` 高是刻意的。** 给一个没人能辩护的标签比承认判不了更糟。回之前先看 stance：对着 `about_self` 回「唱得好」是错位的。
