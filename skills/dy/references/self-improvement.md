# 遇到问题怎么办

`dy` 大部分故障不是命令写错了，是抖音页面变了。这个文件说的是页面出问题时怎么判断、怎么绕、什么时候该报。

## 先分清三种情况

| 现象 | 通常是 | 你该做的 |
| --- | --- | --- |
| 偶发失败，重试就好 | 页面还在加载 / 过渡期 | 等一秒再试一次 |
| 稳定失败，同一个错误码 | 页面结构变了 | 停下来，报告 |
| 结果是 `delivery_uncertain` | 发出去了但证实不了 | **不要重发**，核对收据 |

`dy diagnostics` 会告诉你哪些失败在重复。一次失败不算，重复才算。

## 配置了错误码之后

`dy diagnostics` 报告的是这台机器上记录过的失败。新装的话它是空的——这正常，不是坏了。

看输出里的三个东西：

- **`candidates`** — 反复失败的命令。同一个命令同一个错误码出现多次才值得看。
- **`slowdowns`** — 一直成功但越来越慢的命令。没有错误码，只有时间能看出来。
- **`review.suggested`** — 候选多了它会建议你做点什么。

## 修好之后

`dy diagnostics-ack <命令>` 记一条「此刻修好了」。它之前的失败归档为 resolved，不再排在前面；它之后再失败会让命令重新出现，所以这个标记掩盖不了回归。

有 `--error-code` 可以只标某一个错误码。

## 页面事实

真实页面上验证过的限制，写在 `platform-facts.md`。遇到奇怪的行为先读那个文件——很可能已经记录过了。

## 不要做的事

- **不要为了消除报错而绕路。** 换个 request ID 重发、把 `delivery_uncertain` 当失败重试、用昵称代替 ID——这些会让问题更糟。
- **不要根据一次失败就改判断。** 页面在过渡期会返回看起来像错误的状态。
- **不要从截图推断内容。** 直播画面是 canvas，读不到字；猜错比不猜更糟。
- **不要用手写 `querySelector` 的判断替换 CLI 的。** 代码里的 `find()` 带 `visible()` 过滤和相邻滑片排除；自己探 DOM 时拿到的是另一个元素，量出的坐标可能是负的，于是误判成「页面坏了」。要看真实状态，用 `dy page facts`，或者照抄 `src/page/dom.ts` 的过滤条件。
- **不要拿文档里的选项代表实际行为。** `catalog.ts` 描述的动作和 `validate.ts` 的校验会各自漂移：`video.digest` 一直写着 `--frames 0`，而校验层下限是 1，两者对不上很久了。跑一次比读三遍可靠。

## 想反馈问题的话

这个仓库是开源的，欢迎提 issue 和 PR。

报问题时带上：`dy --version`、系统和 Chrome 版本、去掉正文的命令、结构化 `error.code`，以及这次是页面真机还是测试页复现的。**不要附 Chrome profile、cookie、私信正文或原始本地状态。**

源码里的 `AGENTS.md` 是开发规范。

但改代码不是使用 `dy` 的前提。绝大多数问题用上面的办法就能过去。
