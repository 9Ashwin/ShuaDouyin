# 浏览与成长

## 每一轮的原则

使用 CLI 返回的稳定 ID。采样画面不等于完整观看，评论和私信按用户授权执行。

每轮浏览后调用 `growth review`，按返回顺序处理活动记录；`event:<账号>:<id>` 是操作素材的来源，不自动证明内容正确。

## 看作品

**先判断值不值得看，再决定看多深。** 空刷就是每条都只看开头，十几条下来什么都不知道。

```bash
dy video digest
```

一条命令拿到「这条在讲什么」的最小证据：标题、时长、采样画面、评论区摘录。约 3–4 秒。

**采样位置怎么来的：** 落在中间 80% 里，避开开头的封面语和结尾的求关注。帧数跟着时长走（见下），不是固定的三帧。实测一条 4 分钟英语视频，采样到的字幕分别是「不适合像我这样的人」「一天天一点点积累的」「人们经常问我学英语的诀窍是什么」——拼起来就是完整观点，比标题「第30集 B1听力挑战」信息量大得多。

**按长度分档：**

采样数跟着时长走，不是固定三帧：

| 时长 | 帧数 | 说明 |
| --- | --- | --- |
| < 15s | 0 | 短内容本身就是全部，`frames: []` 配 `limitations` 说明原因 |
| 15–45s | 1 | 取正中 |
| 45s–3min | 3 | 分布在中间 80% |
| > 3min | 每 2 分钟 +1，上限 8 | 20 分钟的访谈取 8 帧 |

**不要用三帧衡量长视频。** 半小时的演讲取三点，等于只看开场、中间一瞥、结尾，论证全丢。既然命令已经按长度算好了，读 `frames` 的长度就知道有没有看够。

**`--frames N` 可以压过自动值**，但最低 1 帧。只想看一个位置就传 1。

**图集是另一回事。** `digest` 遇到图片帖会逐页截图，一页都不少，因为整条作品就是那组图。

**短作品没有帧不等于没看。** `frames: []` 配上「< 15s」的限制说明是设计如此。别当成采样失败去重试。

**论坛区比标题更接近真相。** 一条手势舞标题是「我的世界你就是那中心点」，评论区里作者在问「这一版萌还是上一版萌」——那是连载作品，标题没说。看 `stance` 判断观众在说什么：`about_work` 才是在聊作品，`about_self` 是在聊自己。

**省时间的顺序：** 评论（1 次调用）→ 决定要不要采样 → 采样。评论经常比画面更快告诉你这是什么。

`video observe` 截取浏览器视口：滚动后画面可能不包含作品，暂停时还可能重复，须逐帧确认实际内容。`digest` 的帧也一样——它是采样，不是对整条作品的判断。

## 互动前

重新核对作品、评论或会话的稳定 ID。页面变化就放弃旧决定，不要拿旧决定套新页面。

**推荐流里读到的作者和标题可能来自相邻滑片。** 实测一次 `video.info` 给出了作品 A 的 ID，却配着相邻滑片作品的标题和作者——两个作者都是真的，一个属前一张滑片，一个属后一张。

核对身份不需要换页——工具也没有换页去某条作品的命令。直接再读一次 `video.info`：`slide.id` 稳定、`video_selection.ambiguous` 为 false，就是同一条。

写命令自己也会核对：`video like` / `comment post` / `video steer` 在点击前都比对当前作品 id，对不上就拒绝，不会点错。

评论和聊天回应对方的具体内容，不编造经历、听到的声音或看过的画面。没有合适内容可以不发，这是常态。

**不要把自己的调试过程写成评论。** 「测试一下」「验证能否发送」「第一次就该成功」这类句子对外部读者毫无意义：它们出现在真实作品下面，会让人莫名其妙，而且公开可见、撤不回。评论是给作者和其他观众看的，测试是给自己看的，两者不能混。

需要验证发送链路时，用 AI 测试群，不要拿陌生人的作品当试验田。确实要在评论区验证时，写一句哪怕普通但成立的回应（对内容本身说的话），而不是写「在测功能」。

**发完评论不需要跳详情页去核对。** `comment post` 的返回值里就有答案：

| 返回 | 意思 | 该做什么 |
| --- | --- | --- |
| `confirmed: true` | 页面读到了这条、且带自己的标记 | 结束，继续刷 |
| `delivery_uncertain` | 可能发出去了，页面当时证明不了 | 核对收据和页面，**不要重发** |

`confirmed: true` 已经包含了「读到了新行、文本完全一致、是本人发的、页面标记为已发送」这四件事，是这条命令能给出的最强结论。再跑一次 `comment list` 去「确认一下」不会让它更真。

真正需要核对的是 `delivery_uncertain`，而且核对的对象是**收据**（`dy receipt get <request-id>`），不是重新发一遍。

## 分享

分享前判断是否符合对方当前话题和兴趣：

- `chat share` 是文字链接
- `chat forward` 是原生作品卡片

面板变化不是送达证据。结果不明时核对收据和页面，不换 request ID 重发。

## 发图片

用户要求发送图片时，可以先由当前 agent 的图片生成能力产出本地图片。

```bash
# 私信
dy chat image --conversation-id <会话ID> --image <文件路径> --request-id <唯一ID>
# 作品顶层图片评论
dy comment image --video-id <作品ID> --image <文件路径> --request-id <唯一ID>
```

评论支持 PNG/JPEG，私信还支持 GIF。先用 `--dry-run` 核对文件与目标。正式操作会检查已有草稿、目标和图片预览。

`delivery_uncertain` 需要核对收据与页面，不能自动重发或说成已送达。图文作品发布需先查看当前命令能力，不要假称已经支持。

## 按任务选路

「刷一下」和「找一个人」不是同一件事，但默认都会调 `feed next`。先说你这一轮要交付什么，再选来源。

| 你要的 | 从哪开始 | 别做的 |
| --- | --- | --- |
| 弄清一个问题 | `context show` → `search` → `video digest` | 只堆标题；把平台的 AI 回答当结论 |
| 找合适的人 | 已有候选 / `user.search` → `person read` → 他的作品 | 靠共同关键词、点赞数或私信数量判断 |
| 跟进一个有上下文的人 | `social due` → `social list` → 必要的话读会话 | 一直刷等回复；转去随机找人 |
| 有限探索 | `feed sweep` 小批 | 硬刷够条数；每条都写成长记忆 |

**推荐流不是万能的。** 它给的是平台想让你看的，不是你要找的。要回答一个问题或找一个人，搜索比推荐流直接。

## 一轮怎么走

```bash
dy browse start --budget 30 --minutes 5 --text-file plan.json
```

计划写清四件事：什么模式、这轮交付什么、候选要满足哪几条、什么情况下停。写一次不能改——改交付条件就是换一轮。

然后每一批：

1. **先扫，别先深读。** `feed sweep` 或 `search` 拿一批候选，`video digest --frames 0` 只读标题和评论。
2. **只对少数候选深读。** 一批 5 个里深读最多 2 个。深读是为了补上还缺的那条 criterion，不是为了更了解。
3. **记下判断。**

```bash
dy browse checkpoint <round-id> --text-file batch.json --if-match <revision>
```

每条 criterion 只能是 `supported` / `not_supported` / `unknown`。前两个必须引用真实事件，没有证据就写 `unknown`。**写 `unknown` 不丢人，编一个 `supported` 才是这轮白做的原因。**

`progress.qualified` 就是这轮交付了多少：所有 criterion 都 supported 且没被 exclude。重复提交同一个人不会算两次。

4. **看 `progress.advice` 决定下一步。**

| advice | 意思 | 接下来 |
| --- | --- | --- |
| `target_reached` | 够了 | 交付，别再刷 |
| `no_progress` | 连续几批没增加 | 换来源，或者如实说没找到 |
| `change_route` | 换路次数用尽 | 收尾，交付已有的 |
| `continue` | 还没够但还在进展 | 下一批 |

初始值是每批 5 个、深读最多 2 个、连续 2 批无进展换路、最多换路 2 次。这些是实验参数，不是真理；按任务调。

**达标就停。** 预算是上限不是目标，刷够预算但没找到东西，就该说没找到，而不是继续刷到有。

## 收尾

```bash
dy browse end <round-id> --outcome partial --reason "两次换路后只有 2 个候选符合条件"
```

有计划的一轮必须给 `outcome`。`completed` 要求 checkpoint 里的 qualified 数真的达到目标，否则会被拒——这是记录一致性检查，不是内容判断。

`partial` 是诚实的交付：给出了找到的，也说清了缺什么。`blocked` 是外部挡住（登录、验证、页面故障），`cancelled` 是用户叫停。
